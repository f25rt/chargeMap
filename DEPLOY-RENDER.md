# Deploying ChargeMap to Render

Render deploys each service separately (it does **not** use `docker-compose`). The
`render.yaml` **Blueprint** in the repo root declares all services so Render provisions
them together:

- **chargemap-api** — Spring Boot backend, built from the root `Dockerfile` (Docker runtime)
- **chargemap-redis** — managed Redis (Key Value) for rate limiting
- **chargemap-web** — the Vite SPA as a Static Site, which **rewrites `/api` → the backend**
  (same-origin, so no CORS changes needed)

MongoDB is **not** on Render — use MongoDB Atlas.

---

## Why you saw a "Dockerfile parse error"

This repo has **two** Dockerfiles (`./Dockerfile` for the backend, `frontend/Dockerfile`
for the frontend). If you create a Render service manually without pointing it at the
right Dockerfile + root directory, Render can try to build the wrong context and fail to
parse it. The root `Dockerfile` itself is valid (it builds locally).

**Fix:** deploy via the **Blueprint** (`render.yaml`) below, which names each service's
Dockerfile path and context explicitly — no auto-detection guesswork. (If you must create
services by hand, set the backend's **Dockerfile Path** to `Dockerfile` and **Root
Directory** to the repo root, and deploy the frontend as a **Static Site**, not Docker.)

## One-time deploy (Blueprint)

1. Push the repo (with `render.yaml`) to GitHub/GitLab.
2. Render Dashboard → **New +** → **Blueprint** → connect the repo. Render reads
   `render.yaml` and shows the three services.
3. Before/at first deploy, set these **secret** env vars (they're marked `sync:false`, so
   Render prompts for them):
   - **chargemap-api → `MONGODB_URI`**: your Atlas SRV string with the db name, e.g.
     `mongodb+srv://<user>:<pass>@<cluster>.mongodb.net/chargemap?retryWrites=true&w=majority&appName=ChargeMap`
   - **chargemap-api → `CHARGEMAP_CRYPTO_KEY`**: `openssl rand -base64 32`
   - **chargemap-api → `CHARGEMAP_SUPERADMIN_EMAIL`**: the initial super-admin login email
   - **chargemap-api → `CHARGEMAP_SUPERADMIN_PASSWORD`**: a strong password for it
   - **chargemap-web → `VITE_MAPBOX_TOKEN`**: your Mapbox publishable token
   - (`JWT_SECRET` is auto-generated by Render; Redis host/port are auto-wired.)

   On first startup the backend creates exactly **one SUPER_ADMIN** from those two vars and
   nothing else — stations, rewards, and other users all start empty. Log in as that super
   admin and use the **Admins** view to create admin accounts.
4. Click **Apply**. Render builds the backend image, the Redis instance, and the static site.

## Important: the `/api` rewrite target

`render.yaml` rewrites `/api/*` on the web service to
`https://chargemap-api.onrender.com/api/*`. Render derives that hostname from the service
**name** (`chargemap-api`). If that name is already taken on Render, your backend URL will
have a suffix (e.g. `chargemap-api-abcd.onrender.com`). If so, open `render.yaml`, update
the two `destination:` URLs to your actual backend URL, and redeploy — or rename the
service so it gets the clean hostname.

To find the real backend URL: Render Dashboard → chargemap-api → the URL shown at the top.

## Atlas network access

Add Render's egress to Atlas → **Network Access**. Render's static outbound IPs are listed
per-region in your service's **Connect / Outbound** info; add those, or use `0.0.0.0/0`
for a quick test (tighten later). Unlike your local machine, Render's network won't have
the TLS-inspection issue you hit locally, so Atlas should connect fine.

## Free vs paid tier

- `plan: starter` (in `render.yaml`) keeps services warm.
- If you switch the backend to **free**, it **spins down after ~15 min idle** and cold
  starts take 30–60s for a Spring Boot jar (the first request after idle will be slow, and
  the health check may flap). Fine for a demo; use `starter`+ for anything real.

---

## Production data

The backend runs with `SPRING_PROFILES_ACTIVE=prod`, so the demo seeders do **not** run.
A fresh production database is bootstrapped with exactly **one SUPER_ADMIN** (from
`CHARGEMAP_SUPERADMIN_EMAIL` / `CHARGEMAP_SUPERADMIN_PASSWORD`) and nothing else — stations,
rewards, and other users are empty. The super admin then creates admins from the **Admins**
view in the dashboard; admins manage their branches from there.

---

## Updating

With `autoDeploy: true`, pushing to the connected branch redeploys automatically. Otherwise
use **Manual Deploy** in the dashboard.
